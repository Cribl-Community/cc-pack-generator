# AI-generated sample library

Everything in this directory was **generated by an AI model**, not captured from a
real device. It is kept separate from the other two sample sources on purpose:

| Directory / file | What it is | Trust |
|---|---|---|
| `config/sample-library/` | Sample events mined from real Cribl packs | real data |
| `config/source-samples.json` | Real vendor logs (splunk/security_content) | real data |
| **`config/ai-samples/`** | **AI-generated, machine-verified** | **synthetic** |

Sample resolution prefers real data and only falls back to this library, so a
generated sample never shadows a real one. If nothing here matches either, the
app generates a fresh sample and (in standalone mode) stages it for review.

## Why keep them in git at all

Generating a good sample costs an AI call and can fail in ways that only show up
much later as a pipeline that extracts nothing. Once a sample is verified, it is
worth keeping for everyone: committing it means every user and every fresh clone
gets it without paying that cost again, in both run modes, with no API token.

## What "verified" means

Nothing lands here unless `verifyGeneratedSample()` (`src/sample-library.ts`)
accepted it. Each file records which check ran, in `verification.method`:

- `parser-emulation` — the strongest. The sourcetype's real `regex_extract` /
  `serde` functions were run over the events locally and did extract fields.
- `source-expectation` — the parser can't be emulated (it extracts through a
  `lookup` or `code` function), so the events were held to the wire format
  declared in `GOLDEN_SOURCE_EXPECTATIONS` — the same check that guards the
  golden path.
- `structure` — no parser knowledge for this sourcetype at all. Only says the
  events are well-formed, non-duplicated, self-describing log data. It does
  **not** say they match what the real vendor emits.
- `none` — nothing could be checked. Present only if promoted deliberately.

A `structure` or `none` sample is the most likely to be wrong. Start there when
something downstream looks off.

## Adding a sample

Generated samples are staged in `.cache/ai-samples-pending/`, never written here
directly — what lands in git stays a human decision.

```bash
npm run samples:review              # what is staged, with its verification
npm run samples:promote <key>        # or --all
```

## Clearing the queue: four verdicts

A review has four honest outcomes, and each has its own command so the queue can
always be emptied without overstating what you concluded.

| Verdict | Command | On the screen | Blacklists | Comes back? |
|---|---|---|---|---|
| It is right | `samples:promote <key>` | Promote to library | no | it is in the library |
| It is wrong | `samples:reject <key> --reason=` | Reject & blacklist | **yes, permanently** | never |
| Not ruling on it | `samples:discard <key>` | Remove from queue | no | yes, silently |
| I cannot tell yet | `samples:defer <key> --reason=` | — (CLI only) | no | yes, with your note attached |

`reject` deletes the file, drops it from `index.json`, and records its content
fingerprint in `rejected.json` so the same events can never be re-promoted. A plain
`git rm` also works, but the sample can then come back on the next run — prefer
`samples:reject`. Both `reject` and `defer` require a reason.

In the review screen the third button is **Remove from queue**, which is `discard`: one
click, no prompt, nothing blacklisted. Staging is a cache, so removing costs one
generated file and forecloses nothing — the same sample can be staged and reviewed
again later. Use it for any row you do not want to rule on; use `samples:defer` from the
CLI when the doubt itself is worth handing to the next reviewer.

### Deferring — the verdict for an unclear sample

`reject` is permanent and `discard` records nothing, so an unclear sample used to
have only two bad options: blacklist a fingerprint on a suspicion, or delete the
file and lose the doubt with it. The next generation then stages the same source
again and the next reviewer starts the same investigation from nothing.

`samples:defer` takes it out of the queue, blacklists nothing, and writes the open
question to `deferred.json`. When a sample for that key next appears, `samples:review`
prints your note and says whether the content is **new** (the fresh sample you were
waiting for) or the **same** one again (the generator repeated itself, so nothing has
improved). Promoting or rejecting the key clears the entry, so `deferred.json` only
ever lists questions that are still open.

It is keyed by sample key rather than content fingerprint on purpose: a regenerated
sample has different content, so a fingerprint-keyed note would never be found again
— which is the exact problem it exists to solve. Nothing in `deferred.json` gates a
promotion.

Keys are `<sourcetype>` or `<sourcetype>::<wireFormat>` for sources that emit
more than one format; on disk `::` is written `__` (same convention as the
shared golden store).
